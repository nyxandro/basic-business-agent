# basic business agent

Открытая база, из которой под каждую организацию (заказчика) собирается свой бизнес-агент: веб-чат с интерактивными ответами, сотрудники с ролями и отделами, админка без разработчика, учёт и лимиты расходов на модели в рублях, доступ агента к CRM и почте под личным доступом сотрудника, фоновые задачи, скрытие персональных данных от модели. Каждое действие во внешней системе — только после «Да» сотрудника. Одна установка — одна организация.

Стек: TypeScript strict, Node 24 исполняет `.ts` напрямую (без сборки). Сервер — Hono + Mastra 1.83 (агенты, память, рабочая папка, скиллы) + CopilotKit runtime 2 (AG-UI). Вход — Better Auth. Модели — только через шлюз LiteLLM v1.109.1. БД — Postgres 17 + pgvector, свои SQL-миграции. Интерфейс — React 19, react-router 8, Vite 8, CopilotKit react-core 2 (headless). Песочница скиллов — bubblewrap. Тесты — Vitest 5 и Playwright.

## Неочевидное

- **Шлюз.** Все вызовы моделей и распознавания идут через LiteLLM с личным ключом сотрудника (одна команда на организацию). Образ закреплён по digest во всех трёх compose-файлах; обновление — осознанное, с чтением исходников новой версии.
- **Модели — в базе, не в файлах.** Админ заводит их в «Нейросети»; сервер переносит их в шлюз (`store_model_in_db`) и сверяет при каждом старте. Любое изменение шлюза — через одну очередь `core/models/gateway-writer.ts`: сначала шлюз, потом наша база. Сверка трогает только деплойменты с меткой `bba_owner` этой установки (в тестах — своя метка у каждой тестовой базы).
- **Предел длины ответа** (раздел 8.19) хранится в `app.models.max_output_tokens`. Берётся из справочника шлюза при добавлении модели и уходит в деплоймент шлюза (`max_tokens`), а не в запрос Mastra. Без него Groq молча режет ответ на 2 048 токенах. Деплойменты `groq/…` получают `reasoning_format: parsed`, иначе Qwen 3.6 пишет рассуждения прямо в текст ответа. Ключ новой модели проверяется с тем же пределом и `reasoning_format`: проба LiteLLM сама ставит `max_tokens: 16`, предел ей передаётся в `model_info.health_check_max_tokens` (если в шлюзе есть деплоймент той же модели провайдера, LiteLLM берёт его `model_info`); отказ разбирает `core/models/check-failure.ts` — по тексту до трассировки стека, которую LiteLLM дописывает к ошибке.
- **Учёт и сбои приходят от шлюза:** `generic_api` шлёт успехи на `/app/api/internal/usage`, каждую неудачную попытку — на `/app/api/internal/account-events` (общий секрет `LITELLM_CALLBACK_SECRET`, снаружи эти адреса закрыты Caddy).
- **Пул ChatGPT.** Аккаунт подключается кодом устройства на сайте OpenAI. Токены зашифрованы в `app.chatgpt_accounts`, рабочая копия — файл в томе `chatgpt-auth`, общем с шлюзом; шлюз сам обновляет в нём токен, сервер при старте забирает более свежий. Аккаунт выводится из пула по второму 401 через минуту охлаждения без успеха между ними.
- **Оборванный ответ модели** (раздел 9.1). LiteLLM не повторяет поток, который уже отдал слова, а встроенный повтор Mastra не узнаёт кадр ошибки шлюза внутри потока — поэтому у агента свой `StreamErrorRetryProcessor` (`core/runtime/stream-retry.ts`): обрыв повторяется 1 раз на той же модели, и с запасной тоже (на неё Mastra при обрыве не переключается). Обрывок с экрана убирает наше событие `bba.message_discarded` (`core/chat/discards.ts`): адаптер `@ag-ui/mastra` своих событий не пропускает и показывает ответ Mastra под производными номерами (`<номер>-agui-text` после инструментов) — убирать по номеру ответа Mastra нельзя, сотрутся инструменты прежних шагов. Одно обращение к модели — не дольше 5 минут (`MODEL_CALL_MAX_MS`); поток, молчащий 60 с при открытом соединении (так зависали Groq и neuraldeep), обрывает сам шлюз — `stream_timeout` у каждой модели (`GATEWAY_TIMEOUTS`, `core/models/gateway-sync.ts`), кадр ошибки 408 внутри потока, дальше обычный повтор; Mastra тайм-аут `stepMs` не повторяет. Неудачный ход Mastra дописывает в историю через ~80 мс после конца потока. Слои A2UI, которые среда CopilotKit включает сама по каталогу из браузера (оставлены — решение владельца), при быстром обрыве съедают начало ответа на живом экране; после перезагрузки оно на месте. «Ответить заново» — по номеру вопроса, только где повтор поможет (`ANSWER_AGAIN_CODES`) и не после действия по «Да» в этом ходе.
- **Протокол шлюза не передаёт картинки в ответах инструментов.** Поэтому картинки модели показывает наш `view_image` (процессор `core/sandbox/workspace.ts`), картинки из вложений уходят вместе с сообщением, а встроенному `read_file` Mastra запрещено отдавать картинки и сырые байты (иначе 1,5 МБ уходят текстом и переполняют окно модели).
- **Скиллы:** архив в `app.skills`, распаковка в `APP_SKILLS_DIR/<sha256>/<имя>/`. Mastra берёт скилл только из папки с его именем — другая раскладка молча оставляет агентов без скиллов.
- **Скиллы документов — системные** (раздел 8.18): `core/system-skills/{docx,pptx,xlsx,pdf}` — копия anthropics/skills без правок (коммит в `core/system-skills/README.md`, там же — как обновлять), в базе их нет, `skillsFor` даёт их всем первыми; выключить, заменить, удалить, занять их имя — `APP_SKILL_SYSTEM`. Их инструкции ждут установленными LibreOffice, pandoc, poppler, qpdf, tesseract, библиотеки Python и пакеты Node (`docx`, `pptxgenjs`, `sharp`, `react-icons`) — сети в песочнице нет; без них сервер не стартует (`APP_SANDBOX_UNAVAILABLE`). Песочница Mastra монтирует из `/etc` только отдельные файлы — `/etc/fonts` и `/etc/libreoffice` добавлены (`SANDBOX_SYSTEM_PATHS`), иначе LibreOffice без шрифтов. Файл для сотрудника — инструмент `show_file` (блок «Скачать») и `GET /app/api/threads/:threadId/file`.
- **Поиск** (раздел 8.21). Видимый текст сообщений — `app.message_texts` (с 18.11 — и содержимое таблиц, карточек, графиков, выбора, форм и имя файла, 8.28), словарь слов переписки для исправления опечаток — `app.search_words`; обе ведёт триггер `app.keep_message_text` на `mastra.mastra_messages` в транзакции сообщения. Миграции идут раньше, чем Mastra создаёт свои таблицы, поэтому триггер ставит сервер при каждом старте (`core/search/message-texts.ts`), там же дописывает пропущенное. Триггер не смеет ронять запись сообщения: на любом сбое — предупреждение в журнале базы, не ошибка. Индексы GIN — `fastupdate = off`: с очередью вставок поиск после всплеска сообщений длился секунды. Опечатка в переписке сначала исправляется по словарю, потом ищется прямо; одного `pg_trgm` для опечаток мало (замер 16.11). Файлы в базе не хранятся — поиск при каждом запросе обходит папки (`walkRegularFiles`); `inline=1` у скачивания открывает на месте только PDF. Транслит — пакет `iuliia` (15 систем) и своя обратная таблица в `core/search/variants.ts`; `@copilotkit/markdown` сервера — той версии, от которой зависит `react-core` (тест сверяет).
- **Память экранов** (раздел 8.22). `useLoad(load, key)` — TanStack Query: ключ называет данные и всё, от чего зависит загрузчик (`['project', id]`); без ключа — свежие при каждом открытии (проверки, ссылки пароля, «Ждёт подтверждения» и все экраны-формы: форма из памяти показала бы значения до сохранения, и следующее «Сохранить» тихо их откатило бы — новой форме ключ не давать). Память одна на сессию и очищается при смене вошедшего сотрудника (`auth/session.tsx`); компоненту в тесте без сессии — `WithMemory` (`web/src/test/memory.tsx`). Без повторов при сбое и без обновления при возврате во вкладку; `structuralSharing: false` — экраны узнают «загружено заново» по новому объекту (панель проектов, страница проекта). Ключи проекта — `web/src/projects/queries.ts`, их же берёт загрузка при наведении. Полосок-заглушек нет: пока грузится — ничего, дольше секунды — `DelayedBar`.
- **Хранилище файлов** (раздел 8.23). С подключённым бакетом файлы лежат только в S3, на диске — рабочая копия области (папка разговоров сотрудника или проект целиком) на время работы и 10 минут после. Любое место сервера, которое трогает файлы, сначала держит область: `storage.hold(area, 'read'|'write')` и `release()` (ход агента — до конца хода, после корзины). Новый код, читающий или пишущий файлы рабочей папки, без удержания с бакетом сломается: прочитает пустую папку или запишет файл, который никуда не уйдёт. Удаление из бакета — только из полной копии (отметка `.storage.json` / `.storage-files.json` вне папки агента); папка без отметки сливается, бакет не теряет файлов. Рабочие папки `.snapshots`, `.renders`, `.computer` не хранятся. Удержания считаются в памяти одного процесса.
- **Почта** (раздел 8.24). Ящики — `app.mail_accounts`, пароль и токены зашифрованы. Инструменты агента `mailbox_*` есть только у того, у кого работает ящик; `mailbox_send` — через «Да». Порты — только почтовые (`IMAP_PORTS`, `SMTP_PORTS`; тестам разрешены порты GreenMail). Тестовый почтовый сервер не умеет XOAUTH2 — проверка входа по токену в тестах подменяется (`mailCheck`). Вход Microsoft — только через сайт (OAuth), его приложение заводит администратор.
- **Папка с компьютера** (раздел 8.25) — инструменты браузера (`useFrontendTools`): модель их вызывает, ход кончается вызовом, браузер отвечает и продолжает ход. Копия прочитанного документа — `.computer/<путь>` в рабочей папке (`POST /app/api/threads/:threadId/computer-file`).
- **Память** (раздел 8.26). Записи — `app.memory_entries` (у проекта или у сотрудника), номера — из `app.memory_counters`, не переиспользуются. Читать и менять — только через `core/memory/entries.ts`; память проекта на маршрутах — только через `core/projects/access.ts`. Рабочая память Mastra выключена (`createMemory`), и это не всё: адаптер `@ag-ui/mastra` читает её в обход выключения и возит через «состояние агента» — `state` и `STATE_SNAPSHOT` срезаны в `core/chat/copilot.ts`, не возвращать. Агент правит запись только в той версии, что видел (снимок версий кладёт слой промпта в контекст запроса). Инструменты памяти — только агенту чата (`runKind = chat`), `project_memory` — только в разговоре проекта; ошибки — модели текстом `{ error, code, message }`. Что куда писать, задают описания инструментов и раздел «Память» правил ядра: на живой модели «запомни» о работе уходило в личную память, пока в описании было «личные договорённости». Порядок «сначала запись, потом ответ» держат правило ядра, описания обоих инструментов и строка `note` в ответе инструмента после записи (раздел 8.3): с одним правилом ядра `qwen3.8-flash` (основная модель установки разработки с 16.11) писала ответ вместе с записью и дописывала «Готово — записал» в 14 ходах из 32, с тремя — в 3 из 32; своего условия остановки в цикле нет (решения владельца 15.11 и 18.11). `note` — единственное поле результатов инструментов, которому агент следует (правило «Чьи указания»): его текст постоянный, тексты записей в него не класть.
- **Просмотр документов** (раздел 8.27). Код выхода `soffice` — 0 и при неудаче (файл с паролем, обрезанный архив): успех — только PDF на выходе. Режим «лист целиком» (`SinglePageSheets`) упирается в страницу PDF ~14 400 пт: больший лист LibreOffice уменьшает, а с ~1 000 строк молча обрезает, и выводит скрытые и пустые листы по странице на лист — поэтому `core/preview/sheets.ts` до превращения считает размеры листов (большие книги, `.xls`, `.ods` — страницами печати), а страницы скрытых листов снимает `qpdf` (в образе qpdf 11.3: исключений `x` в диапазоне нет — видимые страницы перечисляются). Новый формат Office с паролем — контейнер OLE (`D0 CF 11 E0`), распознаётся до LibreOffice. PDF.js — только сборка `legacy` (обычная 6.5 падает на телефонах); его папки шрифтов и декодеров — `/pdfjs/…` (`web/vite.config.ts`), Caddy на пропавший файл отвечает страницей с кодом 200 — `pnpm smoke` это проверяет. Готовые PDF — `<tmp>/bba-previews`, ключ — опись хранилища (`storage.stat`), не содержимое: повторный показ не читает файл. Скачивание — всегда `attachment` (`inline=1` убран, F22). Открытие просмотрщика — запись истории с тем же адресом (`location.state.documentViewer`): «Назад» телефона закрывает его. Все форматы через настоящую песочницу — `pnpm preview:check` (с 19.11 — и текст для модели, 8.29).
- **Прошлые разговоры** (раздел 8.28). Каждый запрос к разговорам — с `"resourceId" = userId` (`core/history/store.ts`): пути «найти разговор по номеру» без условия на сотрудника нет, чужой номер — тот же `APP_NOT_FOUND`, что и несуществующий. Что видел сотрудник — список известного (`core/history/transcript.ts`): новый блок интерфейса без своей строки роняет тест по `GENUI_TOOL_IDS`; таблица в ответе инструмента (`{ table }`) — тоже блок. Заявка «Да» становится `approved` до запуска действия, а сбой действия пишется только в журнал — итог берётся из самого вызова (`output-error` / `{ error: true }`), отказ — `output-denied`, `declined` с `APP_CHAT_SUPERSEDED` — «отменено новым сообщением», с `APP_TASK_DELETED` — «фоновую задачу удалили»; вопрос в чате без ответа так и остаётся `pending` после `expires_at` — читается как истёкший. Текст в ответе инструмента режется только `sliceWhole` (`core/history/read.ts`): половинка эмодзи делает JSON сообщения, который Postgres не принимает, и ответ агента выпадает из поиска. Номер сообщения — место среди всех сохранённых сообщений разговора по `createdAt`, `id`, одинаковый в поиске и чтении. Текст переписки в ответе инструмента — только в полях `transcript`, `title`, `text`, `fragment`: маскирование пропускает `type`, `role`, `id`, `data`, `url` и другие `SKIPPED_KEYS`. Поиск агента (`findConversations`) никогда не отдаёт исправленных слов — словарь опечаток общий на организацию. Список и строка «сообщения 1–N тебе не видны» — только основному агенту в разговоре: обработчику слоёв передаётся `level`, строка — в `processLLMRequest` рядом со временем (число меняется каждый ход, системный промпт — нет). Mastra хранит ход агента одним сообщением: 30 последних сообщений — около 15 ходов. Видимый текст для поиска (`app.part_visible_text`, миграция `0028`) включает блоки интерфейса — перечень инструментов там тот же, что в `transcript.ts`.
- **Вложения** называются в тексте сообщения блоком «Вложения:» — формат в `contracts/src/chat.ts` (`withAttachments`, `splitAttachments`), его разбирают и интерфейс, и сервер. В запросе к модели блок ищется в каждой текстовой части сообщения отдельно (`attachmentsOf`): строка времени и текст документов — отдельные части; склейка частей ломала разбор, и с 14.11 по 19.11 картинки вложений не доходили до модели.
- **Быстрое чтение вложений** (раздел 8.29). Обработчик `core/doctext/excerpt.ts` стоит первым — до слоёв промпта (строка времени) и маскирования; картинки — тоже до маскирования (имя файла с телефоном). Программы разбора пишут в файл, а не в вывод: песочница Mastra хранит только последний 1 МиБ вывода. Текст делается в песочнице при первом обращении и лежит неделю в `<tmp>/bba-texts` по версии файла; отказ тоже кэшируется. Word — `pandoc -s` (без `-s` теряется абзац «Заголовок»); Excel — CSV LibreOffice с языком ru-RU в его профиле (`LANG=ru_RU` в песочнице ломает выгрузку), скрытые листы отбрасываются по `sheetNames`; PowerPoint — `slide_text.py` скилла `pptx` (папка его скриптов открыта песочнице только на чтение); PDF — `pdftotext -layout` (таблицы целы, две колонки читаются поперёк). LibreOffice — общая очередь с просмотрщиком (2 запуска на установку). Обработчик картинок в тестовом приложении — только с `sandbox: true`.
- **Возможности агента** (раздел 8.30). Значение `{ web, commands }` агента кладёт каждая точка входа хода (`REQUEST_KEYS.abilities`): чат, «Да»/«Нет», фоновая задача и её продолжение, черновик промпта; подагенты работают с ним же. Наша функция `tools` агента без значения останавливает ход громко — `enabled` у инструментов рабочей папки Mastra получает простой объект и любое исключение молча превращает в «выключено». Строки `app.agent_abilities` пишет старт сервера значениями `AGENT_ABILITY_DEFAULTS` — смена значений по умолчанию не трогает заведённых агентов. Без команд: нет `execute_command` и соседних, нет системных скиллов документов (`skillsFor(…, { documents })`), правила о программах (`core/prompts/rules-commands.md`) заменены строкой, подсказки и пометки документов не предлагают скилл.
- **Интернет агента** (раздел 8.30). У основного агента только `web_research`; исследователь (`core/web/research.ts`) — свой `Agent` поверх `generate`, не встроенные подагенты Mastra: те отдают подагенту всю переписку и хранят его ветку под владельцем `<сотрудник>-<агент>`, которую не находит удаление. Источники — прочитанные страницы следа поиска (`WEB_TRAIL_KEY` в контексте исследователя). Поиск — `/v1/search/web-search` шлюза личным ключом, поисковик описан в файле настроек шлюза (`search_tools`, `buildLiteLLMConfig`), за ним SearXNG; запись учёта поиска (`call_type: asearch`) не пишется. Тестовый шлюз ходит в заглушку SearXNG на порту 39997 — её слушает только `core/models/gateway.test.ts`; остальные тесты подменяют поиск и страницы (`createTestApp({ web })`). `web_fetch` соединяется только через `publicLookup` (адрес проверяется на самом соединении и на каждой переадресации; адрес-число — `assertPublicLiteral`); локальный сайт тестов проходит по `testSite`. HTML страницы пишется во временную папку как `page.webpage` — `core/doctext` читает её `trafilatura` (основной текст), без основного текста — `markitdown`. Поле адреса — `address`: поля `url` маскирование пропускает. VPN машины разработки подменяет адреса части сайтов на 198.18.x.x — такие сайты здесь «внутренние». Шаги исследователя (запросы и страницы) пишут `web_search` и `web_fetch` в след `core/web/trail.ts`; в чате каждый шаг сразу уходит в браузер событием `CUSTOM` `bba.web_progress` с номером вызова `web_research` — его вставляет прослойка агента в `core/chat/copilot.ts` (функция `REQUEST_KEYS.webProgress`), потому что `core/chat/stream.ts` вставляет события только между строками потока, а пока инструмент работает, строк нет. Блок в браузере — `web/src/chat/WebSearch.tsx`; шаги на время окна — `web/src/chat/web-progress.ts`, навсегда — в результате вызова (`steps`, `ms`); модель их не видит — `toModelOutput` инструмента, Mastra хранит проекцию в сообщении.
- **Каждый запрос агента несёт около 12 000 токенов входа** (правила ядра, промпт агента, инструменты): почти вся цена сообщения — вход.
- **Агенты сотрудника** — по его отделам (`department_agents`); суперадмин видит всех. Интерфейс никогда не открывает недоступного агента: запомненный агент берётся, только если он есть у человека.
- **Название разговора** (раздел 8.16) — не инструмент агента, а служебный запрос `core/chat/naming.ts` рядом с ходом, пока у разговора `metadata.titleSource = 'first-message'` (у разговоров до 15.11 источника нет — их имена не меняются сами). Имя пишется прямым SQL в `mastra.mastra_threads` при условии источника (`core/memory/titles.ts`), чтобы не перезаписать ручное имя и не сдвинуть разговор в «Недавних». Служебный запрос помечен заголовком `x-bba-call: thread-title`; модель-заглушка отвечает на него по своему сценарию (`scriptNaming`, по умолчанию «-») и не трогает ходы агента. Метаданные разговора меняются только частичной записью Mastra (`updateThread({ id, metadata })`) — передать имя, прочитанное заранее, значит затереть новое.
- **Общий проект** (раздел 8.20). Кто видит проект, решает только `core/projects/access.ts` (`SEES`): создатель, «всей организации», люди и отделы списка `app.project_shares` — считается при каждом запросе, отдел «живой». Нигде больше не проверять проект по `user_id`. Папка проекта — всегда у создателя (`/workspace/<создатель>/projects/<id>`), поэтому корень хода — `projectOwnerId` из контекста запроса. Проект и папка берутся один раз в начале хода (`runProjectOf`): закрытие доступа посреди ответа его не обрывает; ответ, ждавший «Да», дорабатывается в своём проекте (`approval_requests.project_id`) — Mastra продолжает его со своими сохранёнными инструкциями. Место в панели, закрепление и «новое» — `app.project_places` у каждого человека. Связь разговора с закрытым или архивным проектом не удаляется — состояние вычисляется (`threadProjectState`); удалённый навсегда оставляет в связях коллег `lost_project_name`.
- **Корзина проекта** (раздел 8.20). Удаление агентом ловится не перехватом команд, а слепком: перед ходом в проекте — жёсткие ссылки на файлы в `.snapshots/<id>`, когда агент сам закончил ход — не по обрыву соединения: CopilotKit доводит ход без браузера (прослойка AG-UI с `finalize` в `core/chat/copilot.ts`, `settleRun`; конец фонового запуска) — пропавшее уходит в `trash/` (`settleSnapshot`). Папку проекта, куда пишет агент, читать и менять только через `core/workspace/held-folder.ts`: агент может в любой момент подменить папку ярлыком или файл — каналом (FIFO). Работа с файлами Mastra сама создаёт свою папку при запуске и родительские при записи — папку исчезнувшего проекта убирает разбор слепка и `recoverProjectFolders` при запуске. Запись поверх файла на месте из скрипта прежнюю версию не оставляет. Уборка — раз в час (`startTrashPurge`).
- **Значок агента** (раздел 8.17) — у каждого агента строка `app.agent_marks` (без строки — искра), приходит в чат со списком агентов (`/agents` → `mark`); выключатель «показывать» — одна строка `app.interface_settings`, приходит с `/me`. Картинка агента отдаётся только тому, у кого он есть, суперадмину и праву «Агенты». Вкладки страницы агента — один маршрут `agents/:agentId/:tab?` и общий ключ рамки (`agentPageKey`): иначе рамка админки пересоздаёт страницу и несохранённый промпт пропадает. Картинку готовит браузер (`web/src/admin/agent-image.ts`: квадрат по центру, 256 px, WebP), сервер браузеру не верит — PNG/JPEG/WebP по первым байтам, до 512 КБ и до 256×256 точек по заголовку файла (`core/interface-settings/image-size.ts`; иначе маленький по весу файл огромных размеров роняет вкладки чата у всех). Иконку из `AGENT_ICONS` убирать только вместе с миграцией, переводящей её агентов на `spark`, иначе список агентов упадёт у всех. Образец в другой теме — атрибут `data-theme-scope` (`tokens.css`).
- **Тестовый LiteLLM общий для всех тестовых файлов.** Модели-заглушки (`test-paid`, `test-sub` и др.) записаны в его файле, а не в базе; сверка их не трогает (`fileModelIds`). Порты 39999 (приём учёта и сбоев) и 39998 (заглушка ChatGPT) слушает только `core/models/gateway.test.ts`; другой тестовый файл их занимать не должен.
- **Анимации в CSS-модулях.** Сборщик переименовывает имя анимации в имя модуля, а общие `@keyframes bba-*` лежат в `web/src/ui/theme/base.css`: из `*.module.css` писать `animation: global(bba-…) …`, иначе анимация молча не идёт. Блик печатающегося ответа (`web/src/chat/AnswerText.tsx`) — градиент сквозь буквы: элементу со своим фоном внутри ответа нужен свой градиент или свой цвет (блок кода), иначе его текст исчезает (`web/src/chat/answer-text.module.css`).
- **Prettier в проекте не настроен** — не запускать: он переформатирует файлы под 80 колонок. Форматирование руками в стиле соседнего кода.

## Правила кода

- Только стираемый синтаксис TypeScript (`erasableSyntaxOnly`): без `enum` и без свойств в параметрах конструктора. Импорты — с расширением `.ts`. Файл кода — до 800 строк.
- Границы импорта проверяет `tooling/architecture`: `core/` не импортирует плагины и зону установки; плагины и зона установки берут из ядра только `core/<модуль>/public/`; `web/` импортирует только `@bba/contracts`.
- Ошибки на границах — `AppError` (`core/errors/app-error.ts`): код `APP_*`, текст для человека по-русски, следующий шаг; исходная ошибка — в `cause`. Новые коды — в `core/errors/catalog.ts`.
- Обязательной настройки нет — остановка с `APP_CONFIG_INVALID`, без значений по умолчанию. В `.env` — только секреты и адреса подключений; поведение — в `config/` и коде.
- Миграции — новые SQL-файлы `core/db/migrations/NNNN_имя.sql`, каждая в своей транзакции; применённую не меняем. Схемы: `app` — наши таблицы и Better Auth, `mastra` — Mastra, `litellm` / `litellm_test` — шлюзы.
- Тексты интерфейса — в `web/src/i18n/ru.ts`; журналы и технические сообщения — по-английски с кодом `APP_*`.
- Секреты (ключи провайдеров, токены, `device_auth_id`) — только зашифрованными в базе; в журнал, ответы, аудит и тексты ошибок не попадают (в журнал — имя ошибки, не её текст, если в нём может быть кусок файла).

## Проверки

- Обязательные для шага: `pnpm typecheck && pnpm lint && pnpm test`. `pnpm test` — сервер (~1,5 мин, параллельно) и интерфейс.
- Точечно: `pnpm exec vitest run core/models/gateway.test.ts`, интерфейс — `pnpm -C web exec vitest run src/admin/accounts.test.tsx`.
- Тестам сервера нужен `pnpm dev:db` (Postgres, тестовый LiteLLM и тестовый почтовый сервер). Тест базы создаёт себе пустую базу через `createTestDatabase()` и удаляет её.
- `pnpm test:e2e` — 37 сценариев в браузере (~10 мин); стенд — с настоящей песочницей (документ Word по словам «документ Word»; «в интернете» — поиск через заглушки поиска и страниц `standWeb`). Сам поднимает стенд на :3000 и :8080 — перед запуском остановить `pnpm dev`/`pnpm stand` или гонять во временной копии на 3100/8180 (раздел 22 спецификации). `test` и `expect` сценарии берут из `tests/e2e/helpers.ts`: он закрывает окна сценария после него.
- `pnpm preview:check` — все форматы просмотрщика (13 образцов `core/preview/fixtures`) и текст для модели (21 проверка, ещё образцы `core/doctext/fixtures`) через настоящую песочницу; в `pnpm test` из них только три (параллельный прогон под нагрузкой и так падает по времени); `pnpm smoke` запускает её в образе.
- `pnpm smoke` — сборка образов и проверка установки отдельным проектом Docker `bba-smoke` (порт 18080), в конце удаляется. Нужна сеть до npm.
- `pnpm check:public` — вся история без данных заказчиков; список имён — локальный `.public-check/forbidden-words.txt`, не публикуется. Хук перед отправкой проверяет то же самое.
- Сначала тест, который падает, потом код. Модель в тестах — заглушка (LiteLLM `mock_response`, `core/models/fake-openai.ts`, `core/models/fake-chatgpt.ts`); настоящие ключи в тестах не нужны.

## Порядок работы

- Ответы владельцу, документы в `docs/`, коммиты и задачи — по-русски. Владелец — технический продакт, код руками не пишет: сначала последствие, потом механизм.
- Коммит и отправка — после каждого законченного шага; сообщение `Шаг N: что сделано` (или суть исправления). Шаг отмечается в чек-листе #2, итог — комментарием в задаче.
- Решения владельца — в спецификации (строки «решение владельца ДД.ММ»). Отступление от плана — комментарием в задаче; если оно меняет устройство — поправить и соответствующий раздел спецификации.

## Локальный стенд

- На http://localhost:8080 смотрит владелец. Не останавливать и не подменять то, что там запущено, не предупредив; логины везде одинаковые (ниже).
- **Установка разработки** (по умолчанию): `pnpm dev` = `dev:stack` (LiteLLM разработки на :4000, база `litellm_dev`) + `dev:app` (сервер :3000, `node --watch` — правки подхватывает сам) + `dev:web` (Vite :8080, проксирует `/app/api` на :3000). Основная модель — `qwen3.8-flash` у neuraldeep (с 16.11), рядом заведены Qwen 3.6 27B и Qwen 3.8 27B через Groq (раздел 8.19); ключ только в базе разработки, зашифрован. Скиллы документов — системные, загружать не нужно; библиотеки Python, пакеты Node и программы песочницы (`core/sandbox/apt-packages.txt`) ставит `pnpm skills:setup` — программы без `sudo`, в `.venv-skills/system` (`tooling/sandbox-programs/install.ts`).
- **Стенд для e2e**: `pnpm stand` + `pnpm dev:web` — свежая тестовая база (удаляется при остановке), модель-заглушка отвечает по ключевым словам, пул из трёх аккаунтов ChatGPT в заглушке OpenAI. Те же порты, что у `pnpm dev`: одновременно не запускать.
- Логины (пароль `correct-horse-battery`): `igor@example.com` — суперадмин, `olga@example.com` — «Продажи», `petr@example.com` — «Бухгалтерия», `demo-admin2@example.com`. В установке разработки их ставит `pnpm dev:people` (повторный запуск возвращает всем этот пароль).
- Postgres разработки: `127.0.0.1:54329`, быстрый SQL — `docker exec bba-dev-db-1 psql -U bba -d bba`. Тестовый LiteLLM — :54400, LiteLLM разработки — :4000 (мастер-ключ в `.env`).
- `.env` должен содержать все переменные `.env.example`; без них `dev:stack` и сервер останавливаются с `APP_CONFIG_INVALID`.
- Том базы `bba-dev_db-data` не удалять и не пересоздавать без предупреждения владельца.

## Скиллы агента (для работы в этом репозитории)

- Скиллы проекта — в `.agents/skills`, ссылки — в `.claude/skills`, установка — в `skills-lock.json`. Ставятся командой `DO_NOT_TRACK=1 npx skills add <репозиторий> --skill <имя> -a claude-code codex -y`.
- `mastra-*` — ссылки на документацию внутри установленных пакетов Mastra. После обновления Mastra сначала прочитать, что изменилось, потом опираться. Поведение Mastra и LiteLLM проверять по установленным исходникам, не по памяти.
- Скилл `copilotkit`: не запускать `copilotkit verify` и не подключать MCP-сервер CopilotKit без разрешения владельца — они отправляют данные в CopilotKit.

## Установка и границы

- Выкладки нет: работа заканчивается тестами, e2e и `pnpm smoke`. `deploy/compose.yaml` — установка организации на один сервер (8 ГБ), ни разу не ставилась на настоящий сервер.
- Репозиторий публичный: данных заказчиков в нём быть не должно, в примерах — только вымышленные организации и люди. Материалы заказчиков — в `inbox/` (в `.gitignore`). Ключи и токены — никогда в репозиторий.
- Только с разрешения владельца: влить в `main`, создать PR, удалить тома и данные, подключать внешние сервисы, которые получают данные проекта.
