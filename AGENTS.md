# basic business agent

Открытая база, из которой под каждую организацию (заказчика) собирается свой бизнес-агент: веб-чат с интерактивными ответами, сотрудники с ролями и отделами, админка без разработчика, учёт и лимиты расходов на модели в рублях, доступ агента к CRM и почте под личным доступом сотрудника, фоновые задачи, скрытие персональных данных от модели. Каждое действие во внешней системе — только после «Да» сотрудника. Одна установка — одна организация.

Стек: TypeScript strict, Node 24 исполняет `.ts` напрямую (без сборки). Сервер — Hono + Mastra 1.83 (агенты, память, рабочая папка, скиллы) + CopilotKit runtime 2 (AG-UI). Вход — Better Auth. Модели — только через шлюз LiteLLM v1.109.1. БД — Postgres 17 + pgvector, свои SQL-миграции. Интерфейс — React 19, react-router 8, Vite 8, CopilotKit react-core 2 (headless). Песочница скиллов — bubblewrap. Тесты — Vitest 5 и Playwright.

## Неочевидное

- **Шлюз.** Все вызовы моделей и распознавания идут через LiteLLM с личным ключом сотрудника (одна команда на организацию). Образ закреплён по digest во всех трёх compose-файлах; обновление — осознанное, с чтением исходников новой версии.
- **Модели — в базе, не в файлах.** Админ заводит их в «Нейросети»; сервер переносит их в шлюз (`store_model_in_db`) и сверяет при каждом старте. Любое изменение шлюза — через одну очередь `core/models/gateway-writer.ts`: сначала шлюз, потом наша база. Сверка трогает только деплойменты с меткой `bba_owner` этой установки (в тестах — своя метка у каждой тестовой базы).
- **Предел длины ответа** (раздел 8.19) хранится в `app.models.max_output_tokens`. Берётся из справочника шлюза при добавлении модели и уходит в деплоймент шлюза (`max_tokens`), а не в запрос Mastra. Без него Groq молча режет ответ на 2 048 токенах. Деплойменты `groq/…` получают `reasoning_format: parsed`, иначе Qwen 3.6 пишет рассуждения прямо в текст ответа.
- **Учёт и сбои приходят от шлюза:** `generic_api` шлёт успехи на `/app/api/internal/usage`, каждую неудачную попытку — на `/app/api/internal/account-events` (общий секрет `LITELLM_CALLBACK_SECRET`, снаружи эти адреса закрыты Caddy).
- **Пул ChatGPT.** Аккаунт подключается кодом устройства на сайте OpenAI. Токены зашифрованы в `app.chatgpt_accounts`, рабочая копия — файл в томе `chatgpt-auth`, общем с шлюзом; шлюз сам обновляет в нём токен, сервер при старте забирает более свежий. Аккаунт выводится из пула по второму 401 через минуту охлаждения без успеха между ними.
- **Оборванный ответ модели** (раздел 9.1). LiteLLM не повторяет поток, который уже отдал слова, а встроенный повтор Mastra не узнаёт кадр ошибки шлюза внутри потока — поэтому у агента свой `StreamErrorRetryProcessor` (`core/runtime/stream-retry.ts`): обрыв повторяется 1 раз на той же модели, и с запасной тоже (на неё Mastra при обрыве не переключается). Обрывок с экрана убирает наше событие `bba.message_discarded` (`core/chat/discards.ts`): адаптер `@ag-ui/mastra` своих событий не пропускает и показывает ответ Mastra под производными номерами (`<номер>-agui-text` после инструментов) — убирать по номеру ответа Mastra нельзя, сотрутся инструменты прежних шагов. Одно обращение к модели — не дольше 5 минут (`MODEL_CALL_MAX_MS`); поток, молчащий 60 с при открытом соединении (так зависали Groq и neuraldeep), обрывает сам шлюз — `stream_timeout` у каждой модели (`GATEWAY_TIMEOUTS`, `core/models/gateway-sync.ts`), кадр ошибки 408 внутри потока, дальше обычный повтор; Mastra тайм-аут `stepMs` не повторяет. Неудачный ход Mastra дописывает в историю через ~80 мс после конца потока. Слои A2UI, которые среда CopilotKit включает сама по каталогу из браузера (оставлены — решение владельца), при быстром обрыве съедают начало ответа на живом экране; после перезагрузки оно на месте. «Ответить заново» — по номеру вопроса, только где повтор поможет (`ANSWER_AGAIN_CODES`) и не после действия по «Да» в этом ходе.
- **Протокол шлюза не передаёт картинки в ответах инструментов.** Поэтому картинки модели показывает наш `view_image` (процессор `core/sandbox/workspace.ts`), картинки из вложений уходят вместе с сообщением, а встроенному `read_file` Mastra запрещено отдавать картинки и сырые байты (иначе 1,5 МБ уходят текстом и переполняют окно модели).
- **Скиллы:** архив в `app.skills`, распаковка в `APP_SKILLS_DIR/<sha256>/<имя>/`. Mastra берёт скилл только из папки с его именем — другая раскладка молча оставляет агентов без скиллов.
- **Скиллы документов — системные** (раздел 8.18): `core/system-skills/{docx,pptx,xlsx,pdf}` — копия anthropics/skills без правок (коммит в `core/system-skills/README.md`, там же — как обновлять), в базе их нет, `skillsFor` даёт их всем первыми; выключить, заменить, удалить, занять их имя — `APP_SKILL_SYSTEM`. Их инструкции ждут установленными LibreOffice, pandoc, poppler, qpdf, tesseract, библиотеки Python и пакеты Node (`docx`, `pptxgenjs`, `sharp`, `react-icons`) — сети в песочнице нет; без них сервер не стартует (`APP_SANDBOX_UNAVAILABLE`). Песочница Mastra монтирует из `/etc` только отдельные файлы — `/etc/fonts` и `/etc/libreoffice` добавлены (`SANDBOX_SYSTEM_PATHS`), иначе LibreOffice без шрифтов. Файл для сотрудника — инструмент `show_file` (блок «Скачать») и `GET /app/api/threads/:threadId/file`.
- **Вложения** называются в тексте сообщения блоком «Вложения:» — формат в `contracts/src/chat.ts` (`withAttachments`, `splitAttachments`), его разбирают и интерфейс, и сервер.
- **Каждый запрос несёт около 7 000 токенов инструкций** (правила ядра, промпт агента, инструменты): сообщение на Qwen 3.8 через Groq стоит около 0,5 ₽, почти всё — вход.
- **Агенты сотрудника** — по его отделам (`department_agents`); суперадмин видит всех. Интерфейс никогда не открывает недоступного агента: запомненный агент берётся, только если он есть у человека.
- **Название разговора** (раздел 8.16) — не инструмент агента, а служебный запрос `core/chat/naming.ts` рядом с ходом, пока у разговора `metadata.titleSource = 'first-message'` (у разговоров до 15.11 источника нет — их имена не меняются сами). Имя пишется прямым SQL в `mastra.mastra_threads` при условии источника (`core/memory/titles.ts`), чтобы не перезаписать ручное имя и не сдвинуть разговор в «Недавних». Служебный запрос помечен заголовком `x-bba-call: thread-title`; модель-заглушка отвечает на него по своему сценарию (`scriptNaming`, по умолчанию «-») и не трогает ходы агента. Метаданные разговора меняются только частичной записью Mastra (`updateThread({ id, metadata })`) — передать имя, прочитанное заранее, значит затереть новое.
- **Значок агента** (раздел 8.17) — одна строка `app.interface_settings`, приходит в чат с `/me`. Картинку готовит браузер (`web/src/admin/agent-image.ts`: квадрат по центру, 256 px, WebP), сервер браузеру не верит — PNG/JPEG/WebP по первым байтам, до 512 КБ и до 256×256 точек по заголовку файла (`core/interface-settings/image-size.ts`; иначе маленький по весу файл огромных размеров роняет вкладки чата у всех). Иконку из `AGENT_ICONS` убирать только вместе с миграцией, переводящей её на `spark`, иначе `/me` упадёт у всех. Образец в другой теме — атрибут `data-theme-scope` (`tokens.css`).
- **Тестовый LiteLLM общий для всех тестовых файлов.** Модели-заглушки (`test-paid`, `test-sub` и др.) записаны в его файле, а не в базе; сверка их не трогает (`fileModelIds`). Порты 39999 (приём учёта и сбоев) и 39998 (заглушка ChatGPT) слушает только `core/models/gateway.test.ts`; другой тестовый файл их занимать не должен.
- **Prettier в проекте не настроен** — не запускать: он переформатирует файлы под 80 колонок. Форматирование руками в стиле соседнего кода.

## Правила кода

- Только стираемый синтаксис TypeScript (`erasableSyntaxOnly`): без `enum` и без свойств в параметрах конструктора. Импорты — с расширением `.ts`. Файл кода — до 800 строк.
- Границы импорта проверяет `tooling/architecture`: `core/` не импортирует плагины и зону установки; плагины и зона установки берут из ядра только `core/<модуль>/public/`; `web/` импортирует только `@bba/contracts`.
- Ошибки на границах — `AppError` (`core/errors/app-error.ts`): код `APP_*`, текст для человека по-русски, следующий шаг; исходная ошибка — в `cause`. Новые коды — в `core/errors/catalog.ts`.
- Обязательной настройки нет — остановка с `APP_CONFIG_INVALID`, без значений по умолчанию. В `.env` — только секреты и адреса подключений; поведение — в `config/` и коде.
- Миграции — новые SQL-файлы `core/db/migrations/NNNN_имя.sql`, каждая в своей транзакции; применённую не меняем. Схемы: `app` — наши таблицы и Better Auth, `mastra` — Mastra, `litellm` / `litellm_test` — шлюзы.
- Тексты интерфейса — в `web/src/i18n/ru.ts`; журналы и технические сообщения — по-английски с кодом `APP_*`.
- Секреты (ключи провайдеров, токены, `device_auth_id`) — только зашифрованными в базе; в журнал, ответы, аудит и тексты ошибок не попадают (в журнал — имя ошибки, не её текст, если в нём может быть кусок файла).

## Проверки

- Обязательные для шага: `pnpm typecheck && pnpm lint && pnpm test`. `pnpm test` — сервер (~1,5 мин, параллельно) и интерфейс.
- Точечно: `pnpm exec vitest run core/models/gateway.test.ts`, интерфейс — `pnpm -C web exec vitest run src/admin/accounts.test.tsx`.
- Тестам сервера нужен `pnpm dev:db` (Postgres и тестовый LiteLLM). Тест базы создаёт себе пустую базу через `createTestDatabase()` и удаляет её.
- `pnpm test:e2e` — 24 сценария в браузере (~6 мин); стенд — с настоящей песочницей (документ Word по словам «документ Word»). Сам поднимает стенд на :3000 и :8080 — перед запуском остановить `pnpm dev`/`pnpm stand`.
- `pnpm smoke` — сборка образов и проверка установки отдельным проектом Docker `bba-smoke` (порт 18080), в конце удаляется. Нужна сеть до npm.
- `pnpm check:public` — вся история без данных заказчиков; список имён — локальный `.public-check/forbidden-words.txt`, не публикуется. Хук перед отправкой проверяет то же самое.
- Сначала тест, который падает, потом код. Модель в тестах — заглушка (LiteLLM `mock_response`, `core/models/fake-openai.ts`, `core/models/fake-chatgpt.ts`); настоящие ключи в тестах не нужны.

## Порядок работы

- Ответы владельцу, документы в `docs/`, коммиты и задачи — по-русски. Владелец — технический продакт, код руками не пишет: сначала последствие, потом механизм.
- Коммит и отправка — после каждого законченного шага; сообщение `Шаг N: что сделано` (или суть исправления). Шаг отмечается в чек-листе #2, итог — комментарием в задаче.
- Решения владельца — в спецификации (строки «решение владельца ДД.ММ»). Отступление от плана записывать в «Сделано … Отступления» шага.

## Локальный стенд

- На http://localhost:8080 смотрит владелец. Не останавливать и не подменять то, что там запущено, не предупредив; логины везде одинаковые (ниже).

## Скиллы агента (для работы в этом репозитории)

- Скиллы проекта — в `.agents/skills`, ссылки — в `.claude/skills`, установка — в `skills-lock.json`. Ставятся командой `DO_NOT_TRACK=1 npx skills add <репозиторий> --skill <имя> -a claude-code codex -y`.

## Установка и границы

- Выкладки нет: работа заканчивается тестами, e2e и `pnpm smoke`. `deploy/compose.yaml` — установка организации на один сервер (8 ГБ), ни разу не ставилась на настоящий сервер.
- Репозиторий публичный: данных заказчиков в нём быть не должно, в примерах — только вымышленные организации и люди. Материалы заказчиков — в `inbox/` (в `.gitignore`). Ключи и токены — никогда в репозиторий.
- Только с разрешения владельца: влить в `main`, создать PR, удалить тома и данные, подключать внешние сервисы, которые получают данные проекта.
