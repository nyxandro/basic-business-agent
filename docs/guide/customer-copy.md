# Копия для заказчика

Как из открытого репозитория собрать установку для одной организации, поставить её на сервер и потом подтягивать улучшения ядра. Пример — вымышленный заказчик «Альфа-Строй».

## Что где живёт

- **Открытый репозиторий** — ядро (`core/`, `web/`, `contracts/`), общие плагины (`plugins/`), демо-установка. Данных заказчиков в нём нет и быть не должно: перед каждой отправкой это проверяет `tooling/no-customer-data` (список имён — локальный файл `.public-check/forbidden-words.txt`, он не публикуется).
- **Копия заказчика** — закрытый репозиторий с общей историей. В ней меняется только зона установки: `config/`, `agents/`, `workflows/`, `skills/`, `custom/`. Код ядра не трогаем — тогда улучшения ядра приходят слиянием без конфликтов.

## 1. Сделать копию

```bash
pnpm customer:new alfa-stroy --plugins mail,bitrix24
```

- Копия появляется рядом с открытым репозиторием (`../alfa-stroy`, другое место — `--target <папка>`).
- Без `--plugins` команда спросит, какие плагины оставить; `--plugins ""` — ни одного.
- Невыбранные плагины удаляются первым коммитом копии. Открытый репозиторий подключён как `upstream`.
- Копируются только файлы из git: материалы заказчиков (`inbox/`) и секреты (`.env`) не переезжают.

Подключите закрытый репозиторий заказчика:

```bash
cd ../alfa-stroy
git remote add origin <адрес закрытого репозитория>
git push -u origin main
```

## 2. Агенты

Агент — папка `agents/<папка>/`:

- `agent.ts` — паспорт: `defineAgent({ id, name, description, model, plugins, readOnly, starters, editable })`. `id` постоянный: им агент связан с отделами, правками промпта и расходами; папку можно переименовать.
- `instructions.md` — промпт агента. Правила ядра (безопасность, подтверждения, данные) добавляются всегда, их не нужно повторять.
- `skills/` — методики компании (скиллы Mastra), `tools/` — свои инструменты агента, `subagents/` — подагенты.
- `readOnly` — инструменты, которые только читают: они работают без «Да». Всё остальное ждёт подтверждения сотрудника.

Уберите удалённые плагины из `agents/*/agent.ts` — иначе запуск остановится с `APP_CONFIG_INVALID` и назовёт файл и поле.

## 3. Настройки установки

- `config/app.ts` — название организации, часовой пояс (месячные лимиты обнуляются в 00:00 1-го числа по нему), что скрывать от модели с самого начала, стартовые лимиты. Дальше маскирование и лимиты меняет администратор в админке.
- Моделей в файлах нет: администратор добавляет их в «Нейросети» — ключ провайдера, цены в рублях, основная и запасная модель. Ключи хранятся зашифрованными в базе, LiteLLM получает их от сервера. Файл `config/models.ts` из этапа 1 нужно удалить: с ним запуск остановится и подскажет, что делать.
- `config/plugins.ts` — настройки оставленных плагинов (каждый проверяет свои при запуске).
- `.env` — только секреты и адреса подключений; поведение задаётся в `config/` и коде.

## 4. Проверить локально

```bash
cp .env.example .env && pnpm install && pnpm skills:setup
pnpm dev
pnpm admin:create admin@example.com "Администратор"
```

В админке: отделы → сотрудники и агенты отделов, роли, лимиты, профиль организации. В чате проверьте агентов; действие во внешней системе должно спрашивать «Да».

## 5. Поставить на сервер

Сервер — одна машина с Docker (по оценке спецификации: 4 ядра, 8 ГБ).

```bash
cp deploy/.env.example deploy/.env       # заполните: пароли, секреты, ключ шифрования, соль LiteLLM, адрес сайта
docker compose -f deploy/compose.yaml up -d --build --wait
docker compose -f deploy/compose.yaml exec app node core/cli/admin.ts create admin@alfa-stroy.example "Администратор"
pnpm smoke                               # проверка сборки и изоляции на копии установки
```

- Модели меняются в «Нейросети» без перезапуска. Сервер при каждом старте сверяет их с LiteLLM. `LITELLM_SALT_KEY` шифрует ключи провайдеров в базе LiteLLM: после добавления моделей его нельзя менять.
- Адрес сайта: `SITE_ADDRESS` — доменное имя (Caddy сам получит сертификат HTTPS) или `:80` за локальным портом. `APP_PUBLIC_URL` должен с ним совпадать.
- Наружу открыт только Caddy: интерфейс и `/app/api`. Адрес учёта расходов LiteLLM (`/app/api/internal`) снаружи недоступен.
- Песочница скриптов скиллов работает внутри контейнера приложения на bubblewrap; контейнеру подключён профиль `deploy/seccomp-bwrap.json` (стандартный профиль Docker плюс 7 системных вызовов изоляции). Если на сервере bubblewrap запрещает AppArmor (так бывает на Ubuntu 24.04) — запасной путь описан в спецификации, раздел 8.9.
- Ключ шифрования: `APP_ENCRYPTION_KEYS="2:<новый>,1:<старый>"` — новый шифрует, старый ещё расшифровывает. Потеря ключа — потеря сохранённых личных доступов сотрудников.

## 6. Обновления ядра

```bash
git fetch upstream
git merge upstream/main
pnpm install && pnpm typecheck && pnpm lint && pnpm test
docker compose -f deploy/compose.yaml up -d --build --wait   # миграции базы выполняются при старте, данные сохраняются
```

## 7. Улучшения — обратно в открытый репозиторий

Улучшили общий плагин или ядро в копии — перенесите изменение в открытый репозиторий отдельной веткой, без файлов и данных заказчика. Решение, нужное только этому заказчику, остаётся в его копии (`custom/`, его агенты и скиллы).
